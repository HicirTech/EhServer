# 对 EhServer 的含义

整个 wiki 里只有这一页是分析：把各专题页的事实，翻译成 EhServer（[#84 dispatcher 模式](https://github.com/HicirTech/Ehviewer-Lab/issues/84)）要面对的事。其他页只记事实。

除非另行标注，本页内容都是【推断】。每条后面的链接指向支撑它的事实页。

## 0. 结论

- **#84 第 1 问（限额按账号还是按 IP 算）有了官方答案，而且偏坏**：图片限额**默认按 IP 计**。只有 Bronze Star（捐 20 美元）或 "More Pages" Hath perk（200 Hath）能把限额绑到账号上（10,000 张，按账号）。对普通账号来说，把所有设备集中到一个家宽出口，等于把原本分散在几个 IP 上的配额合并成一份；请求频率高时，这个 IP 还会被降级到低分辨率。[限额与风控](Limits-and-Anti-Crawling.md)
- **代价不高的解法存在**：Bronze Star 或 More Pages 之后，限额跟账号走，集中不会让总量变差。Bronze Star 还能让账号不受「同 IP 其他人」引起的限制，也不受反爬降级影响。先查账号现状（spike S1），再决定要不要为 dispatcher 买这个。
- **封禁仍然按 IP，而且这个 IP 是家里的**：页面加载过快会先警告、再临时封 IP（社区见过从不到 1 小时到 3 天）。集中之后，所有设备的请求都算在一个 IP 头上，封禁也是全家一起受影响。官方给了明确的节奏（API 连续 4-5 次后等约 5 秒），限速必须是服务端的一等功能。[限额与风控](Limits-and-Anti-Crawling.md)
- **一人一号**：官方规定每人只能有一个活跃账号，账号共享按多开处理会被封号。如果 EhServer 服务多个人，每个人都要用自己的账号，服务端得按用户隔离会话，不能「家里共用一个号」。[限额与风控](Limits-and-Anti-Crawling.md)
- **登录只能走 cookie**：论坛自 2025-12 起有 Cloudflare 挑战，脚本登录返回 403。服务端不做账号密码登录，只接收用户在浏览器里登录后得到的 cookie。[登录与会话](Login-and-Session.md)
- **搬迁面是可数的**：大约 30 个对外请求、6 个 API 方法、22 个解析器，外加一个每页最多 5 轮往返的阅读状态机。[请求清单](Request-Inventory.md)、[阅读方式](Reading-Pipeline.md)
- **最大的长期成本是跟上站点改版**：上游两年里因改版修了约 10 次解析器。集中后只需改一处，但这一处坏了，所有设备一起坏。[解析器与数据模型](Parsers-and-Data-Model.md)
- **法律风险是真实的**：2026-03 FAKKU 的 DMCA 通知（依据反规避条款）已经让 GitHub 封了 FooIbar/EhViewer、Ehviewer-Overhauled，下架了 gallery-dl 的 E-Hentai 提取器，还点名了 LANraragi。`HicirTech/EhServer` 现在是**公开**仓库，而「替多台设备自动访问 E-Hentai 的服务」正是那份通知针对的东西。仓库可见性最好在推送任何代码或 wiki 之前就定下来。[其他客户端与先行实现](Prior-Art.md)

## 2. 搬迁面

- 33 个 `EhEngine` 方法去掉死代码后，大约 30 个对外请求；再加上阅读流水线直接发出的详情 / 单页 / 图片请求，以及缩略图、种子、归档 zip 的裸请求。#84 说的「26 个文件、整个 `client/` 层」指的就是这些。[请求清单](Request-Inventory.md)
- URL 语法不大：一个列表构造器、十几个固定模板，外加若干「从 HTML 里抓出来再原样回放」的链接（翻页游标、归档表单 action、种子链接、原图链接）。这些必须当作不透明字符串保存，不能只存结构化数据。[站点地图](Site-Map.md)
- 死代码不用搬：`getProfile`、`editWatchedTag`、`EhConfig.uconfig()` 等。[请求清单](Request-Inventory.md)
- 客户端落后于站点的地方，服务端从一开始就要跟上：相对路径的缩略图 URL、40 位页 token（`datatags`）、`s.exhentai.org` 上的缩略图要带 cookie、`iq` cookie、官方 API 主机 `api.e-hentai.org`、2024-08 之后的 home.php。[其他客户端与先行实现](Prior-Art.md)、[API](API.md)

## 3. 会话与凭据

- **要保存的**：`ipb_member_id`、`ipb_pass_hash`，加上 `igneous`（里站），以及买过临时配额时的 `iq`。前两个等同于账号密码，存储、权限、备份都要按密码对待。
- **按用户隔离**：一人一号是官方规则。服务多个人时，每人一套 cookie、一份配额、一套失效检测；不同用户的会话不能混用。
- **两站各一份**：客户端在 WebView 和粘贴两条路上，都把凭据复制到 `exhentai.org`。服务端也要这样做；`s.exhentai.org` 也要能用上。
- **只接 cookie，不做密码登录**：论坛的 Cloudflare 挑战让脚本登录不可行。用户在浏览器里登录，把 cookie 交给服务端。`igneous` 的签发和 IP / 地区有关，所以最好在**和服务端同一个出口网络**的浏览器里登录。
- **保护好 `igneous`**：站点可能下发 `igneous=mystery` 之类的无效值，客户端会照单全收、覆盖掉有效值。服务端要拒绝用无效值覆盖；过期时按社区做法刷新（删掉后请求一次里站页面）。
- **必须照搬的规则**：发往 `*.e-hentai.org` 的请求注入 `nw=1`；不指望 uconfig cookie。
- **失效检测要补上**：服务端无人值守，必须主动发现「cookie 失效了」「里站权限没了（Sad Panda / 空页面）」「限额被降级了」「IP 被警告 / 封禁了」这类状态，并通知前端。

依据：[登录与会话](Login-and-Session.md)、[限额与风控](Limits-and-Anti-Crawling.md)。

## 4. 出口、选址与请求头

- **出口用家宽，不用 VPN / 代理**：被滥用的 VPN / 代理 IP 会被反爬锁在 1280x 或 1920x，`igneous` 也常常拿不到。homelab 的家宽出口反而是更好的选择。前提是它能直连 E-Hentai。
- **大概率不用搬**：内置 IP 表、DoH、域前置。如果 homelab 出口在中国大陆网络，问题就变成「homelab 怎么出去」，而上一条又说明代理出口本身有代价，这是需要单独权衡的事。
- **共用 IP 的牵连**：限额和封禁都按 IP。homelab 出口如果还承载家里其他设备的 E-Hentai 流量，大家都在同一个池子里；Bronze Star 能让账号不受别人的影响。
- **必须照搬**：「哪些端点永远在 e-hentai.org」这张表（home、toplist、news、论坛、缩略图），以及 Referer / Origin 的规律。
- **UA 要做决策**：客户端写死 Chrome 118 Windows。服务端可以统一管理，但要不要伪装成浏览器、伪装成哪个版本，代码给不出答案。

依据：[选址与网络](Site-Selection-and-Network.md)、[限额与风控](Limits-and-Anti-Crawling.md)。

## 5. 限额与限速

- **两种预算**：开着 H@H、尺寸不超过 1280x 时，到限额只是降到 1280x，阅读几乎不受影响；原图（存档质量）则每 MB 计 10 点，限额用完后要扣 GP。服务端应该把「阅读」和「存档」当成两种预算来管。
- **全局速率预算**：所有设备、所有画廊、所有用户（同一个出口）共用。参考点：
  - 官方：API 连续 4-5 次后等约 5 秒；以图搜图两次之间等 10 秒；归档每台服务器最多 5 路（FAQ 说下载管理器 4 线程以内）；
  - NekoInverter：同一本画廊内，每个页面请求的发起间隔 1 秒；
  - gallery-dl：请求间隔随机 3-6 秒；
  - LANraragi：3、4、10 秒间隔都有被临时封禁的报告，结论是总量比间隔更关键。

  建议默认值偏保守、可调，间隔和每日总量都要限。NekoInverter 的间隔只在单本画廊内生效，Ehviewer-Lab 的 `download_delay` 只是每个线程各自 sleep，它们都默认只有一台设备在访问。
- **警告和封禁要能识别，并全局暂停**：识别「打开页面太快」的警告和纯文本的封禁页，解析剩余时间，到期前暂停**所有**请求（JHenTai 默认就是暂停全部任务）。HTTP 429 和 `api.e-hentai.org` 的空 200 响应也要当成限流信号。
- **509 和降级是全局事件**：客户端只把 509 当作某一页失败，其他线程照样继续消耗。服务端看到 509 或「IP 被限制」的信号，应该让整个出口进入冷却。
- **避免 `nl` 重试风暴**：每次 `nl` 重载计 50 点。客户端每页最多跑 5 轮，后 4 轮都带 `nl`，所以一页最坏要多花 200 点。服务端要给 `nl` 重试单独设预算。
- **只取一次，就地缓存**：真正计费的是「取单页 / 取图片 URL」，取图片文件不计费。同一张图服务端只解析一次，存下字节，给所有设备复用。
- **官方提供的「正门」**：发现新画廊可以用 RSS（最新 100 本）、sitemap、OpenSearch；整本获取可以用归档、H@H 下载器、种子。按官方的说法，这些都比逐页抓取更不容易触发限制。

依据：[限额与风控](Limits-and-Anti-Crawling.md)、[阅读方式](Reading-Pipeline.md)、[下载、归档与种子](Download-Archive-Torrent.md)。

## 6. 阅读状态机与字节路径

- **有状态，不是 RPC**：一页图最多 5 轮往返，轮与轮之间要带着 showkey、用过的 nl key、上一页的 ptoken。应该在服务端内部完整执行这个状态机，前端只说「给我第 i 页」。如果拆成「前端一步步调 API」，等于把状态机又搬回手机。
- **ptoken 表可以持久化，并在设备间共享**：今天每台设备各取一遍，服务端取一次就够了。这是集中化的真实收益之一。ptoken 是原图 SHA-1 的前 10 位，开了 `datatags` 能直接拿到完整 SHA-1，可以用来做完整性校验和去重。
- **字节路径（#84 第 4 问）的约束**：经 H@H 的图片直链只有 15 分钟有效，所以「服务端解析出 URL、手机自己去拉」只能是即时的，不能缓存 URL；而且这样手机又要访问 `*.hath.network`，和「手机只认识 homelab」的目标冲突。「服务端拉字节、再交给手机」更符合 #84 的方向，代价是 homelab 的上下行带宽。
- **先确认今天的形状**：图片 URL、`showpage` 的 JSON、`nl` 的语义，仓库里只有 2019 年的证据；社区资料能补一部分，但没有一份完整的样本。

依据：[阅读方式](Reading-Pipeline.md)、[API](API.md)。

## 7. 下载调度与归档

- 今天的「同时只下一本、靠前台服务吊住进程、重启不恢复、Android 15 到点停」全是手机的限制。服务端调度器应该是持久队列，能断点续传，有全局限速，有警告 / 509 / 封禁之后的冷却。
- **归档值得作为主力路径之一**：一个 zip 只要少量 HTML 请求，不碰逐页的限额机制。官方价格是每 MiB 20 GP（捐赠者 15 GP），一本 500 MiB 的画廊要 10,000 GP；捐赠者每周有免费额度（Bronze 5 GB 起，只限一年内的画廊）。归档服务器支持按字节范围续传。
- **归档链接的 IP 限制**：一个链接最多被两个 /24 网段使用。服务端取链接、服务端自己下载，最稳；把链接转给手机下载，会多占一个网段。
- **H@H 归档可以和 homelab 结合**：在 homelab 上跑一个 H@H 客户端，再用「H@H 下载器」，等于让 homelab 自己拉整本画廊。健康运行的 H@H 客户端每天还能攒 1,000 MB 起的免费归档额度。代价是要长期运行一个对外服务的 H@H 节点（推荐 443 端口），这是一个独立的运维决定。
- **先例**：[lifegpc/eh-downloader](https://github.com/lifegpc/eh-downloader) 已经是一个「Deno 服务端 + 任务队列 + Swagger API + Flutter 前端」的 E-Hentai 下载服务，在形态上最接近 EhServer，值得在选型前读一遍。JHenTai 的「Archive Bot」则是另一种形态：由服务方持有账号和 GP，客户端只拿一个 API key。

依据：[下载、归档与种子](Download-Archive-Torrent.md)、[其他客户端与先行实现](Prior-Art.md)。

## 8. 解析与站点改版

- **服务端用什么语言写，在这里分量很重**：要么复用这 22 个 Java 解析器（服务端用 JVM），要么重写。重写的成本不在「写」，而在「跟上改版」。复用的代价是把它们从 Android 的工具类（`StringUtils`、`NumberUtils`、`Settings`）里解耦出来，同时补上它们已经落后的地方。
- **把账号显示设置固定下来**：服务端用的是固定的账号，可以在接入时把 uconfig 设成解析器最稳的组合，这样解析器只需要支持一种形状。社区在 2024-10 改版时的应对办法也是固定设置：缩略图大小 Normal、页码标注 None、开启 H@H。另外阅读器设置**不能**是 MPV，否则 `/s/` 页面会变样。表站和里站的配置档是分开的，两边都要设。
- **解析失败要当作告警**：服务端必须区分「真的没有」和「站点改版了」，后者要立刻通知维护者。可以用保存下来的真实页面做回归测试（先清洗掉账号相关值）；EhPanda 连封禁页都存了夹具，这个做法值得照抄。
- **集中的利与弊**：改版时只改服务端，不用每台手机升级 APK；但服务端坏了，所有设备一起坏。

依据：[解析器与数据模型](Parsers-and-Data-Model.md)、[其他客户端与先行实现](Prior-Art.md)。

## 9. 错误模型

服务端必须显式区分下面这些状态，它们对前端和运维来说是完全不同的事件：

- 正常的空结果
- 需要登录、cookie 失效
- Sad Panda（没有里站权限）
- 限额到顶：509，或被降到 1280x
- IP 被反爬降级到低分辨率
- 「打开页面太快」的警告
- IP 被临时封禁，以及解封时间
- 论坛或站点的 Cloudflare 挑战（403）
- GP 不足
- 解析失败（站点改版）
- 网络错误

客户端今天把其中好几种都表现成「空列表」或一段原始文本。依据：[请求清单](Request-Inventory.md)、[限额与风控](Limits-and-Anti-Crawling.md)。

## 10. 端上还剩什么

这是 #84 第 7 问的输入，不是决定。

| 类别 | 例子 | 可能的归属 |
|---|---|---|
| 纯本机 | UI 设置、阅读器手势、解码缓存、搜索建议 | 手机 |
| 本机规则，作用于 E-Hentai 数据 | 屏蔽规则、标签翻译 | 两种都说得通；但屏蔽规则在今天的代码里会**触发请求**（gdata 补全），放服务端更顺 |

| 用户级，但今天只在某台手机上 | 历史、本地收藏、下载标签、阅读进度 | 放服务端才能多设备共享 |

依据：[功能面](Feature-Surface.md)。

## 11. 前端 API 的抽象

- 前端和服务端之间的 API 不应该透传 E-Hentai 的 URL 语法。比如 `f_cats` 是「排除」掩码，这种反直觉的设计应该在服务端翻译掉。这属于 #84 第 3 问「抽象层次」。
- 外部链接识别（用户在浏览器里点了 e-hentai 链接）仍然发生在手机上。手机只需要解析出 gid / token / ptoken 交给服务端，不需要访问 E-Hentai。
- 能用 API 的尽量用 API：JSON 比 HTML 稳。服务端可以只从列表 HTML 取 gid / token，元数据全部用 `gdata` 取（官方文档化，返回字段比客户端用到的多：文件大小、种子、父子版本等）。但每次 API 调用也算一次请求，要计入速率预算。
- `gdata` 里一项 token 失效就会返回错误项，服务端要按项容错，不能像客户端那样整批失败。
- `apikey` 来自页面，生命周期未知；服务端需要缓存它，失效时重新抓详情页。

依据：[站点地图](Site-Map.md)、[API](API.md)。
